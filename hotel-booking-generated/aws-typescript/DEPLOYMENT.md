# Deploying hotel-system to AWS

This guide deploys the generated **CloudFormation stacks** (`infrastructure/*.template.json`),
the **function packages** they run (`infrastructure/assets/`) and the **container images**
(ECR) to AWS.

- **Quickest -- run the generated deploy script**: `deploy.sh` (bash) or `deploy.ps1`
  (PowerShell) run the full bootstrap + package upload + image supply + stack rollout end
  to end. Both are thin entrypoints: each activates the project virtual environment
  (`.venv/`, created on first run) and hands every argument to `deploy.py`, which is the
  deployment itself -- so the two shells cannot behave differently.
- **Manual steps** (below): run every step yourself -- useful for a first deploy or to
  understand what the script automates.

## Managing the deployment

The script takes a **command argument**; with none, it runs `deploy`. Flags may be
written either way -- `--force` and `-Force` mean the same thing -- because the
PowerShell entrypoint forwards its arguments untouched.

| Command | What it does | Reversible? |
|---|---|---|
| `deploy` *(default)* | Deploys the bootstrap stack, uploads the function packages, supplies every container image, then deploys every other stack with `aws cloudformation deploy` in dependency order. Idempotent: an image whose content hash is already in ECR is not rebuilt, and an unchanged package is not uploaded again. | n/a |
| `down --scope clients` | Stops every site: each site stack deploys with `SiteEnabled=false`, which disables its distribution; its bucket and files stay. `down --scope backend`, and `down` with no scope, are refused (see below). | Yes -- `deploy` serves the sites again. |
| `destroy` | Deletes every stack, the last-deployed first, and with it every resource the stacks created -- databases, queues, buckets and everything they hold. The bootstrap stack's buckets (the deployment bucket and the run store, which empties itself a day after its last write) and container repositories are retained. Asks you to type the application name to confirm; `--force` skips the prompt. | **No -- irreversible.** |

```bash
bash deploy.sh                     # provision and roll out
bash deploy.sh destroy             # tear down (prompts for confirmation)
FORCE=true bash deploy.sh destroy  # non-interactive
```

```powershell
./deploy.ps1                       # provision and roll out
./deploy.ps1 destroy               # tear down (prompts for confirmation)
./deploy.ps1 destroy -Force        # non-interactive
```

Two parts of the shared CruftFree deployment vocabulary are **not** implemented here;
`deploy.sh --help` says so, and why:

- `down` of the backend (`--scope backend`, or no scope: stop compute, keep data) would
  change running resources outside the templates that declare them, and the next `deploy`
  would silently restore them.
- `reset` (remove the workload, keep the infrastructure hosting it) assumes a workload
  layer separable from its data stores. Here the databases, queues and buckets *are*
  stack resources, so there is no such layer. Use `destroy` then `deploy`.

## Prerequisites

- AWS CLI configured with valid credentials (`aws sts get-caller-identity` succeeds).
- Docker (with `buildx`) installed and running -- required to build `linux/amd64`
  images even on non-amd64/Windows dev hosts.
- `pip` for the Python that runs `deploy.py`: it installs each function package's
  dependencies as binary wheels for the Lambda runtime.

## Deploy identity rights

Each database's schema task is run by the deploy, on the ECS cluster
`hotel-system-cluster`. Besides the rights to deploy the stacks, the identity that deploys
needs exactly these (`<partition>`, `<region>` and `<account>` are the deployment's):

| Database | Stack | Task definition family | Execution role | Task role | Run-store prefix |
|---|---|---|---|---|---|
| `hotel.StayService.stayDb` | `hotel-system-hotel-stay-service-data` | `hotel-system-hotel-stay-service-data-stay-db-schema` | `StayDbSchemaTaskExecutionRole` | `StayDbSchemaTaskRole` | `hotel.StayService.stayDb/` |
| `hotel.NoticeService.noticeDb` | `hotel-system-hotel-notice-service-data` | `hotel-system-hotel-notice-service-data-notice-db-schema` | `NoticeDbSchemaTaskExecutionRole` | `NoticeDbSchemaTaskRole` | `hotel.NoticeService.noticeDb/` |
| `hotel.PaymentMock.paymentDb` | `hotel-system-hotel-payment-mock-data` | `hotel-system-hotel-payment-mock-data-payment-db-schema` | `PaymentDbSchemaTaskExecutionRole` | `PaymentDbSchemaTaskRole` | `hotel.PaymentMock.paymentDb/` |
| `hotel.EmailMock.emailDb` | `hotel-system-hotel-email-mock-data` | `hotel-system-hotel-email-mock-data-email-db-schema` | `EmailDbSchemaTaskExecutionRole` | `EmailDbSchemaTaskRole` | `hotel.EmailMock.emailDb/` |
| `hotel.ChannelMock.channelDb` | `hotel-system-hotel-channel-mock-data` | `hotel-system-hotel-channel-mock-data-channel-db-schema` | `ChannelDbSchemaTaskExecutionRole` | `ChannelDbSchemaTaskRole` | `hotel.ChannelMock.channelDb/` |

- `ecs:RunTask` on `arn:<partition>:ecs:<region>:<account>:task-definition/<family>:*` for each family above, with the condition `ecs:cluster` = `arn:<partition>:ecs:<region>:<account>:cluster/hotel-system-cluster`.
- `iam:PassRole` on each role above, with the condition `iam:PassedToService` = `ecs-tasks.amazonaws.com`. CloudFormation names the roles: `aws cloudformation describe-stack-resource --stack-name <stack> --logical-resource-id <role> --query StackResourceDetail.PhysicalResourceId` prints a role's name.
- `ecs:DescribeTasks` and `ecs:StopTask` on `arn:<partition>:ecs:<region>:<account>:task/hotel-system-cluster/*`, with the same `ecs:cluster` condition.
- `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject` on `arn:<partition>:s3:::<run store>/<prefix>*` for each prefix above; `<run store>` is the `RunStoreBucketName` output of the `hotel-system-bootstrap` stack.

## Quickest -- the generated deploy script

The deploy script:

1. Deploys the bootstrap stack (`hotel-system-bootstrap`): the deployment bucket
   and one ECR repository per image, before anything is uploaded or pushed.
2. Installs, zips and uploads each function package under `infrastructure/assets/`
   to the deployment bucket, under a key named by the SHA-256 of its zip; an unchanged
   package is not uploaded again.
3. Logs in to ECR (`aws ecr get-login-password | docker login`; the token is valid 12
   hours -- re-run login if a long deploy spans that window).
4. Builds the shared base images (one union-requirements layer per service language),
   each tagged by content hash, and pushes them -- each skipped automatically if the registry
   already holds that hash.
5. Builds and pushes each service image and each Lambda container image,
   tagged by content hash, skipping any image whose tag already exists in its ECR repository.
6. Deploys every other stack with `aws cloudformation deploy`, each after the stacks whose
   exports it imports, passing each the image tags, package keys and run id its template
   declares as parameters: first the data stacks (`DATA_STACKS`: the databases and every
   stack they import from), then the release stacks (`STACKS`).
   Between the two, every database's schema converges (`deploy`'s `converge` step): each
   block's expand applies before any release stack deploys, and its contract once every
   load-balanced service is healthy; a change that needs approval stops the deploy before
   anything applies, unless `--approved` is given.

No image this deploy script builds is ever tagged or pulled using the mutable
`latest` tag -- every image it pushes is pinned to the exact content hash of its
build inputs, so what is running is always traceable to what was built. (This
covers every image the script builds and the stacks run under a resolved-tag
parameter; it does not describe third-party sidecar images a template may reference
directly, such as the AWS-published X-Ray daemon image, which are outside this
script's image-supply stage.)

## Manual steps

1. `aws cloudformation deploy --template-file infrastructure/bootstrap.template.json --stack-name hotel-system-bootstrap --capabilities CAPABILITY_NAMED_IAM --no-fail-on-empty-changeset`
2. `aws ecr get-login-password --region <region> | docker login --username AWS --password-stdin <account>.dkr.ecr.<region>.amazonaws.com`
3. Build and push the base image, then each service/Lambda image, with
`docker buildx build --platform linux/amd64 -t <repo>:<content-hash> ... --push`.
A service image's build binds the base image's bare `FROM` reference to the pushed one with `--build-context <repo>:<hash>=docker-image://<registry>/<repo>:<hash>`, so it also builds on a `docker-container` builder, which never reads the local image store.
4. Install each directory under `infrastructure/assets/` with the Python version and platform `deploy.py` names (`LAMBDA_PYTHON_VERSION`, `LAMBDA_PIP_PLATFORM`), zip it, and `aws s3 cp` the zip to the deployment bucket.
5. For each stack in the order of `DATA_STACKS`, then of `STACKS`, in `deploy.py`: `aws cloudformation deploy --template-file infrastructure/<stack>.template.json --stack-name <stack name> --parameter-overrides <Parameter>=<value> ... --capabilities CAPABILITY_NAMED_IAM --no-fail-on-empty-changeset --s3-bucket <deployment bucket>`. A web static-site stack takes `SiteEnabled=true`.
## Alert routing

Every generated CloudWatch alarm (declared via `alerts { }` blocks) evaluates and fires
regardless of whether anyone is notified. Notification is a separate, optional layer:
declaring one or more entries under `observability.alerting.receivers` (email or webhook)
generates a single shared SNS topic and wires every alarm's `AlarmActions` to it, with one
SNS subscription per declared receiver. With no receivers declared, alarms still exist and
still evaluate -- they are simply **unrouted**: a valid, intentional, documented state, not
an error. Add `receivers` to the system's alerting config and regenerate to route them.

## Troubleshooting

- **`ecr get-login-password` token expired mid-deploy**: re-run the login step; the
  token is valid 12 hours from issuance.
- **A stack still runs the previous image**: the deploy script passes each stack the tag it
  just pushed, as the stack's `<Service>ImageTag` parameter. Compare the parameter in
  `aws cloudformation describe-stacks` with the tag in the registry -- a stale value
  deploys a stale image; there is no mutable `latest` fallback to mask the mismatch.
- **A stack fails to deploy**: `aws cloudformation deploy` prints the failed resource's
  events. Fix the cause and run `deploy` again -- stacks that already match their template are
  left as they are, and no stack after the failed one was deployed. A failed
  preflight stack stops the deploy before any service stack.
- **A function package fails to install**: every dependency must be available as a binary
  wheel for the Lambda Python version and x86_64; nothing is built or fetched when the
  function runs.

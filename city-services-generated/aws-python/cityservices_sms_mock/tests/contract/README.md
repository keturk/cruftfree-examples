# cityservices.SmsMock HTTP contract tests

Generated by CruftFree -- do not edit manually.

These tests call a running cityservices.SmsMock over HTTP and check every declared
route against its contract: the success status, the problem-details answer of
an error, and the shape of each response body. They are a test client, not part
of the service, and are the same whatever language the service is written in.

## What they check

- Every route a client may call answers its declared success status and
  response shape. A resource route whose data the suite can create first
  (`list`, `get`, `create`, `update`, `delete`) must succeed; any other route
  may instead answer a client-error problem other than an authentication
  refusal.
- Every route that requires a credential refuses a call without one, a
  malformed token and a token signed by a key it never trusted, each with 401
  and the unauthorized problem-details body.
- A role-guarded route forbids (403) a caller holding only a role no route
  declares; an optional-auth route answers a caller without a credential.
- A create answers back each member it was sent and refuses an empty input or
  an enum value no member spells with a request-validation problem naming the
  field; a get answers the key it was asked for, and a key no instance has is
  a not-found problem; a deleted instance cannot be deleted again; an instance
  a child still references under `onDelete(restrict)` refuses deletion (409).
- A paginated list answers the window asked for and the default window,
  reports the default and largest page sizes, and refuses an oversize page, a
  negative position and an unknown sort field.
- Values the declaration does not fix (ids, timestamps) are checked by type
  and format only; an object with an undeclared member fails; a computed
  member must agree with its declared expression over the answer's own
  members, where that expression is an enum test, a numeric comparison or a
  text template over text and integer members.

## Running

Python 3.11 or later. From this folder:

```sh
python -m pip install -r requirements.txt
BASE_URL=https://<service origin> python -m pytest
```

`BASE_URL` is required; the suite refuses to start without it. Calls under
`required` or `optional` auth carry a token signed with the published CruftFree
test identity, which only a deployment carrying the injected test identity
provider accepts -- point the suite at a test deployment, never production.

## Running against a deployment with your own credentials

A deployment that trusts only its own identity providers refuses the test identity's
tokens with 401. Run the suite there with tokens those providers issued: name a JSON
file of principals with `CONTRACT_CREDENTIALS`.

```sh
BASE_URL=https://<service origin> CONTRACT_CREDENTIALS=<path to credentials.json> python -m pytest
```

```json
{"principals": [
  {"name": "shopper", "provider": "customer", "roles": ["Buyer"], "token": "<bearer token>", "tenant": "<tenant value>"},
  {"name": "clerk", "provider": "staff", "roles": ["Clerk"], "token": "<bearer token>"},
  {"name": "nobody", "provider": "staff", "roles": [], "token": "<bearer token>"}
]}
```

- `provider` is an identity provider the service declares; `contract.json` names the
  providers each route admits (`providers`) beside its `roles`.
- A positive call presents the `token` of the first principal whose provider the route
  admits and whose `roles` include one of the route's roles (any principal of an admitted
  provider when the route declares no role). The token is opaque: the suite never decodes
  or verifies it, and never writes it to its output, logs or reports.
- A role-guarded route's wrong-role test presents a principal of an admitted provider
  holding none of the route's roles (`"roles": []` is such a principal).
- A test no supplied principal fits is skipped, with the providers and roles it needed as
  the reason; it is never passed or failed. A principal's tokens must be valid for the
  test's whole run.
- A service that reads its tenant from a request header or path is called in the tenant of
  the principal making the call, so give such a principal a `tenant`. A service that reads
  the tenant from the token needs none.
- An `@onboarding` route admits only a caller that belongs to no tenant yet (`contract.json`
  marks it `"onboarding": true`). Declare such a principal with `"tenant": null`; that route
  presents only a principal so declared, and is skipped ("no supplied principal without a
  tenant") when there is none. A principal declared without a tenant is presented to no other
  route of a service that scopes its requests by tenant.
- The refusal tests (no credential, a malformed token, a token signed by a key the
  deployment never trusted) are unchanged and need no principal.
- With `CONTRACT_CREDENTIALS` unset, the suite signs every positive call's token with the
  test identity, as above.

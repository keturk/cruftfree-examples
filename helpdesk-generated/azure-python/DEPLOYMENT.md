# Deploying helpdesk.System to Azure

This guide deploys the generated **infrastructure** (Bicep) and **application code**
(App Service web apps + Azure Functions) to Azure using the `az` CLI.

- **Quickest — run the generated deploy script**: `scripts/deploy.sh` (bash) or
  `scripts/deploy.ps1` (PowerShell) run the entire Option A flow end to end, after
  validating the required environment variables. Both are thin entrypoints: each
  activates the project virtual environment (`.venv/`, created on first run) and hands
  every argument to `scripts/deploy.py`, which is the deployment itself — so the two
  shells cannot behave differently. The same command also manages the deployment's
  lifecycle via a command argument — six of them: `deploy` (default), `down` (pause
  compute, keep data), `destroy` (delete everything), `canary` (the full
  infrastructure minus API Management), `code` (push only changed application code,
  skipping every Bicep stage, when the infrastructure hasn't changed since the last
  full `deploy`), and `verify` (check every app is actually up and fully deployed) —
  documented in [§Managing the deployment](#managing-the-deployment).
- **Option A — Manual `az` deployment** (below): run every step yourself. Best for a
  first deploy, a one-off environment, or when you do not use Azure DevOps.
- **Option B — CI/CD via Azure DevOps**: the generated `azure-pipelines.yml` runs all
  of these steps automatically once you wire up a service connection and a variable group.

> in source control, not here.

## Quickest — the generated deploy script

After meeting the [prerequisites](#prerequisites), the deploy script does everything in
Option A (validate → resource group → **preflight** → **stage 1: foundation** →
**stage 2: full infrastructure** → app code). It checks the required environment
variables first and exits with a clear message if any are missing.

That full pipeline is the **first-deploy** (or infrastructure-changed) path. Once a
resource-group-level infrastructure stamp matches the currently computed hash of
everything under `infra/`, `preflight`'s `what-if` step and stage 1 are both skipped
automatically — see the updated preflight and stage-1 bullets below — and stage 2
still runs (it is what delivers changed image tags or params). Pass `--force`
(`-Force` on PowerShell) to always run the full pipeline regardless of the stamp.

The script is ordered to **fail fast**:

- **Preflight** registers any missing resource providers, purges any soft-deleted Key Vault /
  App Configuration / API Management name collision automatically (a same-name collision is
  nearly always the operator's own teardown residue), and runs `az deployment group what-if`
  to catch template errors — all before provisioning anything. Each purge is verified
  afterward; a purge-protected vault (typically prod) rejects the purge, so it is still
  present after the check and preflight fails loud on exactly that item. Pass `-NoPurge`
  (PowerShell) or set `NO_PURGE=true` (bash) to restore the conservative behavior: report
  every blocking collision with purge/recover guidance and purge nothing.
  `what-if` itself is **skipped** — registration and soft-delete-purge checks still run —
  when the resource group's infrastructure stamp matches the current inputs, with a note
  naming the matched stamp; `--force`/`-Force` always re-runs it.
- **Stage 1 (foundation)** provisions only Key Vault, the database servers and their
  schema workload (the run store, each block's schema identity, and each provisioned
  block's owner role and schema) from `infra/foundation.bicep`. The servers carry the
  offer/quota restrictions and the slowest provisioning, so a region/SKU block (e.g. an
  offer-restricted Postgres region — which `what-if` cannot detect) surfaces in ~1–2
  minutes instead of after dozens of resources; the schema workload is there so every
  block's schema can be read and changed before the application starts.
  Stage 1 is subject to the same stamp-gated skip as `what-if` above: when the stamp
  matches, stage 1 is skipped entirely — the exact same foundation template already
  converged in this resource group, so re-running it would only re-prove what is
  already known — and `--force` restores it.
- **Stage 2 (full infrastructure)** deploys `infra/main.bicep`, which re-declares the
  foundation resources idempotently (a no-op once they exist) and provisions everything
  else. The canary database from stage 1 is the real one — nothing is thrown away.
- **App code push** (see [§7](#7-deploy-the-application-code) /
  [§8](#8-deploy-the-azure-functions) below) assembles the shared web-app dependency
  tree once (and a function-app dependency wheelhouse once), then pushes web apps and
  function apps through the same bounded-wave dispatcher.
  Pass `-TurboScale` (PowerShell) or set `TURBO_SCALE=true` (bash) to temporarily
  scale the App Service plan up to P2v3 for just this push phase, restoring the
  original SKU afterward. OFF by default; sites on the plan restart when the SKU
  changes, and this changes what the plan bills while scaled up, so it is opt-in only.
- **The converge step** brings every database to the schema the application declares,
  around stage 2 and the code push. Once stage 1 is in place, each block's schema workload
  (a container group in the virtual network, signed in as the block's schema identity)
  reads the live catalog, plans it and applies the plan's expand; the block is then read and
  planned again, and the re-plan must hold exactly the first plan's contract changes. Only
  then do stage 2 and the code push run. Once every app passes `verify`, each block's
  contract is applied and its schema verified against the declaration. A change that needs
  approval (a removal) stops the deploy before anything is applied unless `deploy --approved`
  is given; `deploy --plan` prints the plans and changes nothing.
- **`canary` and `code` never start code against a schema it does not find.** `canary`
  expands every block before its stage 2 runs, exactly as `deploy` does, and applies no
  contract: the next `deploy` applies it. It has no `--approved`, so a change that needs
  approval stops it before anything is applied. `code` converges nothing: it reads every
  block first and refuses, naming each block, unless every one already holds the schema the
  application declares; run `deploy` to converge them.

Every run also writes a persistent transcript alongside the normal console output,
at `.deploy-logs/<command>-<UTC yyyymmdd-HHMMSS>.log` under the project root
(created on demand; override the location with the `DEPLOY_LOG_DIR` environment
variable). The console names the transcript's path at the start and end of the run.
If the log directory cannot be written, the script prints one loud note and
continues stdout-only — a broken transcript sink never blocks a deploy.

Every Postgres datasource uses passwordless Entra AD auth, so no admin password
is required. No service applies migrations: the deploy's converge step changes each
database's schema, and each service connects with a login of its own.

```bash
# optional overrides (defaults shown): RESOURCE_GROUP, LOCATION, ENVIRONMENT=dev
RESOURCE_GROUP="helpdesk-system-dev-rg" ENVIRONMENT="dev" bash scripts/deploy.sh
```

```powershell
$env:RESOURCE_GROUP = "helpdesk-system-dev-rg"; $env:ENVIRONMENT = "dev"
./scripts/deploy.ps1
```

## Managing the deployment

`scripts/deploy.sh` / `scripts/deploy.ps1` take a **command argument** that manages a
running deployment without re-deploying it. With no argument the command defaults to
`deploy`. Run `scripts/deploy.sh --help` for the full usage, every flag, and the
environment overrides. Flags may be written either way — `--force` and `-Force` mean
the same thing — because the PowerShell entrypoint forwards its arguments untouched.

The first three are **lifecycle commands** — the same vocabulary every CruftFree-generated
deployment CLI answers, ordered by how much they take away, so the word means the same
thing here as on any other deployment profile. The rest are specific to this platform.

| Command | What it does | Cost impact | Reversible? |
|---|---|---|---|
| `deploy` *(default)* | Provisions infrastructure and deploys all application code. | Brings the deployment online. | n/a |
| `down` | Stops every App Service / Function App site **and** every PostgreSQL Flexible Server in the resource group, then turns off public access to every Static Web App and waits until each refuses a request. `--scope backend` stops the sites and servers alone and leaves the Static Web Apps serving; `--scope clients` stops the Static Web Apps alone. **Nothing is deleted** — storage, databases, and Key Vault are kept. | Stops App Service site and PostgreSQL **compute** charges. The App Service **Plan** still bills while stopped. | Yes — re-run `deploy` (or start the resources) to resume; `deploy --scope clients` serves the Static Web Apps again. |
| `destroy` | **Deletes the entire resource group** (`helpdesk-system-dev-rg`) and everything in it — compute, databases, storage, Key Vault, networking. | Stops all charges. | **No — irreversible.** All data is permanently lost. |
| `canary` | Provisions the full infrastructure **minus API Management** (the long pole), to prove the project is deployable before committing to it. Every resource is the real one; a later `deploy` re-declares them idempotently and adds the gateway. | Brings everything except the gateway online. | Yes — run `deploy` to finish, or `destroy` to tear down. |
| `code` | Delivers only changed application code (container image swap or code-mode push), skipping every Bicep stage. Refuses to run if the infrastructure has changed since the last full `deploy`, or if any database does not already hold the schema the application declares. | No new resources; restarts only the apps whose code changed. | Yes — re-run `code` or `deploy`. |
| `verify` | Checks every web app's readiness route and every Function App's expected function count against what's actually deployed. Read-only; changes nothing. | None. | n/a. |

There is a fourth lifecycle command, `reset`, that this platform does **not** implement:
it means "remove the workload and the data stores this project provisioned, keep the
infrastructure hosting them", and here the data stores *are* provisioned resources
rather than containers on a host, so there is no workload layer to remove that leaves
them standing. `scripts/deploy.sh --help` says so, and points at `destroy` + `deploy`
for a clean installation.

```bash
# Pause to save cost (data retained)
RESOURCE_GROUP="helpdesk-system-dev-rg" bash scripts/deploy.sh down

# Tear everything down (asks you to type the resource group name to confirm)
RESOURCE_GROUP="helpdesk-system-dev-rg" bash scripts/deploy.sh destroy
# non-interactive: FORCE=true RESOURCE_GROUP="helpdesk-system-dev-rg" bash scripts/deploy.sh destroy
```

```powershell
# Pause to save cost (data retained)
$env:RESOURCE_GROUP = "helpdesk-system-dev-rg"; ./scripts/deploy.ps1 down

# Tear everything down (asks you to type the resource group name to confirm)
$env:RESOURCE_GROUP = "helpdesk-system-dev-rg"; ./scripts/deploy.ps1 destroy
# non-interactive: ./scripts/deploy.ps1 destroy -Force
```

> A stopped PostgreSQL Flexible Server is **auto-restarted by Azure after 7 days**. To stay
> paused longer, re-run `scripts/deploy.sh down` periodically, or use
> `scripts/deploy.sh destroy` if you no longer need the data.

## Cost guard (optional budget kill-switch)

`scripts/cost-guard.ps1` arms an automatic **budget cap**: when the subscription's
**actual** monthly spend reaches a threshold, the entire resource group
(`helpdesk-system-dev-rg`) is deleted. Use it on pilot / throwaway environments where a
runaway bill is worse than losing the data. Installing it deletes nothing — it only arms
the guard.

```powershell
# Install with the default $900/month cap
./scripts/cost-guard.ps1

# Install with a custom cap
./scripts/cost-guard.ps1 -MonthlyBudgetUsd 500

# Remove the cost guard (leaves 'helpdesk-system-dev-rg' untouched)
./scripts/cost-guard.ps1 -Uninstall
```

**How it works.** The script deploys a Consumption **Logic App** into a *separate*
resource group (`cost-guard-rg`, so it never deletes itself), wired to an Azure **budget**
alert through an action group. When the budget's *100% actual* threshold is crossed, the
Logic App calls Azure Resource Manager to delete `helpdesk-system-dev-rg`, authenticating
with a managed identity that holds **Owner on `helpdesk-system-dev-rg` only**. You also get
an email when it fires.

| Parameter | Default | Meaning |
|---|---|---|
| `-MonthlyBudgetUsd` | `900` | Monthly cap in USD; the group is deleted at 100% of this. |
| `-ResourceGroup` | `helpdesk-system-dev-rg` | Group to watch and delete (also `$env:RESOURCE_GROUP`). |
| `-NotificationEmail` | signed-in account | Address emailed when the guard fires. |
| `-Uninstall` | — | Remove the guard (budget, role assignment, `cost-guard-rg`). |

> **Irreversible, and not a real-time hard cap.** When the guard fires it permanently
> deletes every resource in `helpdesk-system-dev-rg` — databases, storage, Key Vault.
> Azure cost data lags 8–24h and budgets evaluate only a few times a day, so the deletion
> happens *after* you cross the cap: it limits overage, it does not prevent it.

## Operating-hours scheduler (optional auto start/stop)

`scripts/operating-hours.ps1` keeps `helpdesk-system-dev-rg`'s **compute** running only
during a daily window and **shuts it down outside that window** — no data is ever
deleted. Use it on environments that don't need to run 24/7 (pilots, dev, demos) to cut
cost automatically. Installing it stops nothing immediately; it only arms the schedule.

```powershell
# Install the default window: 08:00–20:00, Mon–Fri, UTC
./scripts/operating-hours.ps1

# Custom window (24h clock) and time zone
./scripts/operating-hours.ps1 -StartHour 7 -StopHour 19 -TimeZone "Eastern Standard Time"

# Custom days
./scripts/operating-hours.ps1 -WeekDays Monday,Wednesday,Friday

# Remove the scheduler (leaves 'helpdesk-system-dev-rg' in its current state)
./scripts/operating-hours.ps1 -Uninstall
```

**How it works.** The script deploys two Consumption **Logic Apps** into a *separate*
resource group (`operating-hours-rg`, so they never stop themselves), each on a weekly
**Recurrence** schedule — one *starts* compute at the start hour, the other *stops* it at
the stop hour. Each enumerates the App Service / Function App sites **and** PostgreSQL
Flexible Servers in `helpdesk-system-dev-rg` and starts or stops them via Azure Resource
Manager, authenticating with a managed identity that holds **Contributor on
`helpdesk-system-dev-rg` only**.

| Parameter | Default | Meaning |
|---|---|---|
| `-StartHour` | `8` | Hour (0–23) compute is started each scheduled day. |
| `-StopHour` | `20` | Hour (0–23) compute is stopped each scheduled day. |
| `-TimeZone` | `UTC` | Windows time-zone id the schedule is evaluated in. |
| `-WeekDays` | `Mon`–`Fri` | Days the schedule fires on. |
| `-ResourceGroup` | `helpdesk-system-dev-rg` | Group whose compute is managed (also `$env:RESOURCE_GROUP`). |
| `-Uninstall` | — | Remove the scheduler (role assignment + `operating-hours-rg`). |

> **Compute only — and the Plan still bills.** Only App Service / Function App sites and
> PostgreSQL Flexible Servers are started/stopped; storage, databases, and Key Vault are
> untouched, so no data is lost. A *stopped* App Service site still bills its App Service
> **Plan** — the real saving here is paused PostgreSQL compute. To stop **all** charges,
> use `scripts/deploy.ps1 destroy` (irreversible).

## Prerequisites

| Requirement | How to check / install |
|---|---|
| Azure CLI 2.60+ | `az version` |
| Bicep CLI | `az bicep version` (auto-installs on first use) |
| Signed in | `az login` then `az account show` |
| **Owner** or **User Access Administrator** on the target subscription / resource group | `az role assignment list --assignee $(az ad signed-in-user show --query id -o tsv) --all -o table` |
| Python 3 (runs the deploy script) | `python3 --version` |
| `python` 3.12 (the services are packaged on it) | the toolchain's own `--version` |

> **Why an elevated role is required.** The infrastructure creates **role assignments**
> (`Microsoft.Authorization/roleAssignments`) that grant each service's managed identity
> access to Key Vault, Storage, Event Hubs, and App Configuration. Creating a role
> assignment needs the `Microsoft.Authorization/roleAssignments/write` permission, which
> the **Contributor** role does **not** have. Deploying as Contributor fails partway
> through with `AuthorizationFailed`. Use **Owner** or **User Access Administrator**.

### Rights the deployment grants the deploying identity

Each RDBMS block's schema workload runs as a one-shot container group inside the virtual
network, started by the identity that runs the deployment. The infrastructure grants that
identity exactly these rights, each a custom role at the narrowest scope that carries it,
and nothing wider:

| Actions | Scope | Why |
|---|---|---|
| `Microsoft.Storage/storageAccounts/blobServices/containers/blobs/read`<br>`Microsoft.Storage/storageAccounts/blobServices/containers/blobs/write`<br>`Microsoft.Storage/storageAccounts/blobServices/containers/blobs/delete` (data actions) | the run store's `runs` container | writes each run's input, reads its output, deletes the run's files |
| `Microsoft.ContainerRegistry/registries/read`<br>`Microsoft.ContainerRegistry/registries/importImage/action` | the composition's container registry | imports each run's images into the registry, by digest |
| `Microsoft.ContainerInstance/containerGroups/write`<br>`Microsoft.ContainerInstance/containerGroups/read`<br>`Microsoft.ContainerInstance/containerGroups/delete` | the resource group | creates one container group per run, reads its state, deletes it |
| `Microsoft.ManagedIdentity/userAssignedIdentities/assign/action` | each RDBMS block's schema identity (`*-schema-<environment>`) | runs the block's container group under its schema identity |
| `Microsoft.Network/virtualNetworks/subnets/join/action` | the subnet delegated to `Microsoft.ContainerInstance/containerGroups` | places each run's container group inside the virtual network |

The deploying identity is resolved when the deployment runs: `scripts/deploy.py` exports
its object id and type as `CRUFTFREE_OPERATOR_PRINCIPAL_ID` and
`CRUFTFREE_OPERATOR_PRINCIPAL_TYPE`, which the parameter files read. Whoever deploys
holds these rights; a deployment by a different identity grants them to that identity.

## Option A — Manual deployment with `az`

### 1. Set deployment variables

```bash
RESOURCE_GROUP="helpdesk-system-dev-rg"
LOCATION="eastus"
ENVIRONMENT="dev"   # 'dev'  -> infra/main.bicepparam
                     # 'prod' -> infra/main.prod.bicepparam
PARAM_FILE="infra/main.bicepparam"   # 'dev' has no suffix; see note below
# The identity running the deployment, granted the rights listed under Prerequisites.
# The parameter file reads both; deploying as a service principal, set its object id
# (az ad sp show --id <appId> --query id -o tsv) and ServicePrincipal instead.
export CRUFTFREE_OPERATOR_PRINCIPAL_ID="$(az ad signed-in-user show --query id -o tsv)"
export CRUFTFREE_OPERATOR_PRINCIPAL_TYPE="User"
```

> The `dev` profile uses `infra/main.bicepparam` (no `.dev` suffix); the `prod` profile
> uses `infra/main.prod.bicepparam`. For `dev`, set `PARAM_FILE="infra/main.bicepparam"`.
> The **resource names** the deploy creates are suffixed with `$ENVIRONMENT`
> (e.g. `helpdesk-ticket-service-$ENVIRONMENT`), so keep `ENVIRONMENT` consistent
> with `PARAM_FILE` throughout. This project was generated for `dev`:
> its services have the Key Vault and App Configuration endpoints of that environment
> baked in, so `ENVIRONMENT` must be `dev` (`scripts/deploy.py`
> refuses any other value). To deploy another environment, regenerate for its profile.

### 2. Passwordless database authentication (nothing to provide)

Every Postgres datasource uses passwordless Entra AD auth — the parameter file
declares **no** `administratorPassword`, so there is no admin-password secret or
environment variable to set. Each App Service instance authenticates to its
database with its managed identity at runtime.

### 3. Validate the templates (deployment-readiness gate)

```bash
az bicep build --file infra/main.bicep          # must exit 0 with no errors
az bicep build-params --file "$PARAM_FILE"
```

### 4. Create the resource group

```bash
az group create --name "$RESOURCE_GROUP" --location "$LOCATION" -o table
```

### 5. (Optional) Preview what will be created

`what-if` is read-only — it provisions nothing:

```bash
az deployment group what-if \
  --resource-group "$RESOURCE_GROUP" \
  --parameters "$PARAM_FILE"
```

> Role assignments show up as **`Unsupported`** in `what-if` output. This is an expected
> Azure limitation — a role assignment's `principalId` is computed at deploy time from the
> managed identity being created in the same deployment, so `what-if` cannot predict it.
> It is **not** an error.

### 6. Deploy the infrastructure

```bash
az deployment group create \
  --resource-group "$RESOURCE_GROUP" \
  --parameters "$PARAM_FILE"
```

> Pass **only** the `.bicepparam` file. Do **not** add `--template-file` or inline
> `--parameters key=value` overrides alongside it — the az CLI rejects mixing a
> `.bicepparam` with other parameter sources. The template is resolved from the
> `using 'main.bicep'` directive inside the parameter file; all values come from the
> parameter file.

### 7. Container image delivery

Each service runs as a **custom container** on Azure App Service, pulling
from the ONE shared Azure Container Registry (ACR) this system provisions
(`helpdesksystemacrf6454ab0<environment>`, the environment label without hyphens). There is no server-side build step and no shared
dependency-share mount — the image is self-contained. The image `ENTRYPOINT`
is authoritative; code delivery is exclusively the **registry pull** Azure
App Service performs when the site's `linuxFxVersion` is updated to
reference a new image tag.

**Shared base images, built and pushed first.** Before any
per-service image, the deploy script builds and pushes ONE shared
per-system base image per service language —
`helpdesk-system-python-base:<union-hash>`— each installed from the union of the runtime requirements of the services
of its language. This is the SAME union-hash algorithm `cruftfree-codegen-docker`
used to bake each exact tag into the `FROM` line of every Dockerfile of that
language, so the reference the deploy script builds always resolves. That
`FROM` line is the bare `<repo>:<union-hash>` reference, which Docker resolves
against the local daemon only, so each base image is loaded locally and tagged
under that bare reference as well as pushed. Build+push is skipped when the
registry already holds that tag; the deploy script then pulls it and tags it
locally instead. Each service build also binds that bare reference to the pushed
image with `--build-context`, because a buildx builder that runs in a container
(the `docker-container` driver) never reads the local image store.

**Per-service images, content-hash tagged.** Each service's image is tagged
with a content hash of its own build inputs — **never** the mutable `latest`
tag (a mutable tag defeats the unchanged-skip check, makes rollback
ambiguous, and hides what a running service actually executes). Build+push is
skipped when the registry already holds the tag.

```bash
az acr login --name "helpdesksystemacrf6454ab0<environment>"
# Shared base image (built once, skipped if the tag already exists):
docker buildx build --platform linux/amd64 \
  -t "helpdesksystemacrf6454ab0<environment>.azurecr.io/helpdesk-system-python-base:<union-hash>" \
  -f python-base/Dockerfile python-base --load
docker push "helpdesksystemacrf6454ab0<environment>.azurecr.io/helpdesk-system-python-base:<union-hash>"
# The service Dockerfiles' FROM is the bare reference -- resolve it locally:
docker tag "helpdesksystemacrf6454ab0<environment>.azurecr.io/helpdesk-system-python-base:<union-hash>" "helpdesk-system-python-base:<union-hash>"
# Then each service's own image. Each --build-context binds the bare FROM
# reference to the pushed base image, so the build also works on a buildx
# builder that cannot read the local image store:
docker buildx build --platform linux/amd64 \
  --build-context "helpdesk-system-python-base:<union-hash>=docker-image://helpdesksystemacrf6454ab0<environment>.azurecr.io/helpdesk-system-python-base:<union-hash>" \
  -t "helpdesksystemacrf6454ab0<environment>.azurecr.io/<service>:<content-hash>" \
  -f <service-dir>/Dockerfile <service-dir> --push
```

**Per-service builds run through a bounded wave, not strictly one at a time.**
After the shared base image above builds and pushes, each service's own image
build dispatches through the same bounded-wave dispatcher the code-push loops
use elsewhere in this file, default wave size **`4`**, overridable via the
`DEPLOY_IMAGE_WAVE` environment variable (`1` restores strictly-serial image
builds) — the same override style already documented for `DEPLOY_WEB_WAVE` /
`DEPLOY_FUNCTION_WAVE`.

**Skip-when-unchanged.** Before building, the script queries
`az acr repository show-tags` for the target tag; when it already exists in
the registry, the build+push for that image is skipped entirely.

**Resolved into the Bicep deployment BEFORE infra rollout.** Every resolved
tag is written into the container-mode `.bicepparam` file's per-service
`ImageTag` parameters, replacing a generation-time placeholder, BEFORE
`az deployment group create` ever runs — the
container-mode analog of the AWS deploy script's `:latest` replacement. This
substitution happens **serially, after every wave finishes** — never
concurrently, and never from inside the wave — because it is a read-modify-write
against the one shared `.bicepparam` file, and doing it from multiple builds at
once would race.


### Verify the deployment

```bash
scripts/deploy.sh verify
```

```powershell
./scripts/deploy.ps1 verify
```

`verify` checks two things automatically: (a) every web app's readiness route
(the route its service's own language serves: `helpdesk-ticket-service` on `/ready`, `helpdesk-knowledge-service` on `/ready`, `helpdesk-notice-service` on `/ready`, `helpdesk-email-mock` on `/ready`) with a bounded retry budget
(`VERIFY_APP_TIMEOUT_SECONDS`, default `300` seconds) to tolerate a cold
container pull after an image swap, and (b) every Function App's
expected-vs-observed function count, failing loud by name on any mismatch —
the check that catches a Function App deployed with zero indexed functions,
a defect a superficial "is the app running" probe would miss entirely. It
exits 1 if any app fails to verify and prints one `ok` line per app on
success.

`verify` also runs automatically at the end of `deploy` and `code` — you do
not need to remember to run it separately after either of those, only when
checking an already-converged environment on its own.

A single web app can still be spot-checked manually without running the full
`verify` command:

```bash
# Print one web app's public URL and probe its health endpoint
app="helpdesk-ticket-service"
host=$(az webapp show \
  --name "$app-$ENVIRONMENT" \
  --resource-group "$RESOURCE_GROUP" \
  --query defaultHostName -o tsv)
echo "$app -> https://$host  ($(curl -sf -o /dev/null -w '%{http_code}' "https://$host/ready" || echo down))"
```

This manual probe does not check Function Apps at all — use `verify` to check
a whole deployment, not just a single web app's HTTP response.

## Option B — CI/CD via Azure DevOps

The generated `azure-pipelines.yml` runs Build → DeployProd on every push to `main`.
Build tests each service on its own language's toolchain. DeployProd checks out the
sources, installs the services' toolchains and runs `scripts/deploy.sh deploy` — the
same script as the manual path above, so CI and a manual deploy package and push every
app the same way. The script's converge step brings every database to its declared
schema, so the pipeline has no migration step of its own. It is fully wired **except** for
two account-specific objects that cannot be generated because they hold
credentials/secrets — you create them once:

1. **Service connection** — name it exactly **`helpdesk-system-azure-connection`**
   (referenced by the pipeline's `azureSubscription` variable).
   In Azure DevOps: *Project Settings → Service connections → New → Azure Resource Manager*,
   scoped to your subscription/resource group. Use a service principal or workload-identity
   federation. The principal needs **Owner** or **User Access Administrator** on the
   resource group (same reason as the manual prerequisites — it creates role assignments).

2. **Variable group** — name it exactly **`helpdesk.System-variables`**
   (referenced by `- group: 'helpdesk.System-variables'`).
   In Azure DevOps: *Pipelines → Library → + Variable group*.

   No secret variables are required: every Postgres datasource uses passwordless

Then commit and push to `main`:

```bash
git add azure-pipelines.yml infra/
git commit -m "Deploy helpdesk.System infrastructure and application code"
git push origin main
```

Monitor the run in Azure DevOps: **Build → DeployProd** (DeployProd targets the
`dev` environment and can be gated with a manual approval).

## Alert routing

Every generated Azure Monitor metric alert (declared and baseline) evaluates and fires
regardless of whether anyone is notified. Notification is a separate, optional layer:
declaring one or more entries under `observability.alerting.receivers` (email or webhook)
generates a single Azure Monitor Action Group and wires every alert rule's `actions` array
to it. With no receivers declared, alerts still exist and still evaluate — they are simply
**unrouted**: a valid, intentional, documented state, not an error. Add `receivers` to the
system's alerting config and regenerate to route them.

## Troubleshooting

| Symptom | Cause & fix |
|---|---|
| `AuthorizationFailed` on role assignments | The deploying identity lacks `roleAssignments/write`. Use **Owner** or **User Access Administrator**, not Contributor. |
| `Only a .bicep template is allowed with a .bicepparam file` | You passed `--template-file` or inline `--parameters` together with the `.bicepparam`. Pass **only** `--parameters "$PARAM_FILE"`. |
| Web app returns 500 | Code not deployed, missing dependency, or missing config. Check Application Insights live metrics / log stream, or the Kudu console at `https://<web-app-name>-$ENVIRONMENT.scm.azurewebsites.net`. |
| Function App: "No handlers found" | `host.json` (zip root) or a handler's `function.json` is missing from the package. Re-run the function packaging step. |
| `deploy` stopped at the converge step | The error names the block and the cause: a change that needs approval (review it with `deploy --plan --approved`, then run `deploy --approved`), a re-plan that differs from the first plan (another deploy or a manual change reached the block between the two reads — run `deploy` again), a lock held by another deploy, or a schema that differs from its declaration after the contract. `schema-read <block>` prints the live catalog. |
